# Почему запись экрана ломается: путь от кадра до MP4

Запись видео кажется естественным расширением скриншота. Если программа уже умеет делать снимок экрана, то дальше вроде бы остаётся просто делать это много раз подряд. На практике именно в этом «просто» и живёт основная боль.

У статического screenshot есть роскошь одноразового действия. Можно один раз получить изображение, один раз сохранить его на диск и закончить. Запись видео — это не один скриншот, а длинная цепочка обязательств:

- регулярно получать кадры
- не отставать по времени
- не ломаться на изменении окна
- не расходиться с FPS
- не уронить процесс
- не записать битый файл
- корректно завершить MP4

То есть видео — это уже не просто graphics task. Это система координации времени.

Особенно это чувствуется на Windows. Как только разработчик идёт в Media Foundation, H.264, RGB32, `IMFSinkWriter`, timestamp в 100-нс единицах и ручную подачу sample-ов, он оказывается в мире, где ошибка может проявиться не как аккуратный `Err`, а как неприятный crash внутри native boundary.

Именно поэтому запись экрана ломается чаще, чем ожидают. Причины почти всегда одни и те же:

- неверный формат входного буфера
- неправильный размер кадра
- odd width/height для H.264
- не та частота кадров
- несогласованные timestamps
- некорректная инициализация COM / MF
- race между stop signal и writer finalization

На бумаге это выглядит как список технических мелочей. На практике каждая такая «мелочь» способна превратить MP4 writer в источник нестабильности.

Ещё один неприятный момент в том, что screen recording почти всегда живёт на границе между несколькими мирами:

- API захвата экрана
- формат внутреннего изображения
- конвертация каналов
- кодек
- контейнер
- файловая система
- UI/управление жизненным циклом записи

Пока приложение делает PNG, можно думать в терминах картинки. Как только оно делает MP4, нужно думать в терминах пайплайна.

И вот здесь появляется самое важное отличие зрелого подхода от наивного. Наивный подход спрашивает: «Как бы мне просто записать видео?» Зрелый спрашивает:

- где в этой цепочке могут расходиться размеры?
- кто отвечает за stop semantics?
- что будет, если screen capture временно не удался?
- можно ли пережить dropped frame?
- как проверить, что итоговый файл вообще валиден?

Это уже не вопрос «написать функцию». Это вопрос построить процесс, который умеет быть устойчивым.

В каком-то смысле запись экрана — отличный инженерный учитель. Она быстро отучает от веры в happy path. Если в screenshot tool можно долго жить на удаче и редких краевых случаях, то видео очень быстро заставляет уважать жизненный цикл, контракты API и системную нестабильность.

Именно поэтому падение в recording path не стоит воспринимать как «ну, что-то там в Windows». Чаще это честный сигнал, что pipeline ещё не выровнен по всем своим границам.

MP4 — это не просто файл. Это результат дисциплины во времени, памяти и форматах.
