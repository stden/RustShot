# Релиз как продукт: инсталлятор, pipeline и дисциплина поставки

Многие разработчики относятся к релизу как к финальной формальности. Настоящая работа, мол, происходит в коде, а installer, CI, артефакты и release page — это уже упаковка. Но как только проектом начинает пользоваться не только автор, становится ясно: релиз и есть часть продукта.

Представим две ситуации.

В первой приложение работает отлично, но:

- инсталлятор ставит его не туда
- автозапуск не появляется
- uninstall оставляет мусор в реестре
- GitHub Release не содержит нужного файла

Во второй приложение чуть менее элегантно внутри, но:

- релиз стабильно собирается
- portable и installer доступны сразу
- версии совпадают
- пользователь понимает, что скачивать

Какой продукт выглядит взрослее? Почти всегда второй.

Именно поэтому release engineering так интересен. Он заставляет посмотреть на программу глазами пользователя, а не автора. Пользователь не видит ваш `impl`, не знает, сколько было красивых refactor-ов и не оценит аккуратный helper в `src/selection.rs`, если скачанный `Setup.exe` не запускает программу после установки.

У таких проектов, как `RustShot`, особенно нагляден один момент: между `cargo build --release` и реальным продуктом лежит большой путь.

Нужно:

- собрать правильный target
- положить `.exe` в правильное место
- построить установщик
- опубликовать portable артефакт
- опубликовать installer
- не перепутать версии
- не сломать autorun

То есть релиз — это отдельный инженерный сценарий, а не хвостик разработки.

Есть полезный психологический сдвиг: относиться к `installer.iss` и release workflow так же серьёзно, как к исходному коду приложения. Не как к второстепенным файлам, а как к месту, где тоже живут:

- архитектурные решения
- ответственность
- риски
- технический долг

Когда разработчик начинает мыслить так, качество продукта резко растёт. Потому что релиз перестаёт быть магией.

Особенно полезно видеть, как release pipeline формирует дисциплину:

- версии не должны расходиться
- артефакты должны называться предсказуемо
- ручные шаги должны быть минимальны
- installer path должен соответствовать build path

Это скучно только на поверхности. На деле тут много красивой инженерии: превращение хаотического процесса в повторяемую поставку.

Есть и ещё одна важная мысль. Плохой релизный pipeline не просто неудобен команде. Он меняет поведение проекта:

- релизы выходят реже
- люди боятся трогать упаковку
- фиксы откладываются
- пользователи получают устаревшие бинарники

То есть качество поставки буквально влияет на скорость развития продукта.

Поэтому installer и CI — это не «последние 10%». Это часть доверия к программе. Пользователь не обязан понимать, как именно вы собирали релиз. Но он очень быстро чувствует, сделан ли выпуск с инженерной аккуратностью.

В этом и состоит взрослая идея: релиз — не упаковка результата. Релиз — это тоже результат.
